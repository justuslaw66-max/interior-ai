# CH-0001 external controls checklist

Repository code now fails closed, but the following platform state cannot be proven from the checkout. A release owner must verify each item for every Vercel project/environment before calling the deployment operationally complete.

| External control | Why it matters | Required secure state | Verified here? |
| --- | --- | --- | --- |
| Vercel Production `APP_ENV` | `vercel.json` intentionally declares staging for the immutable staging flow; production must override it. | Exact value `production` in the production project's Production scope. No surrounding whitespace and no conflicting project override. | No |
| Vercel Preview `APP_ENV` | Preview is not trusted merely because Vercel labels it preview. | Exact value `staging` for approved staging previews, or omit it and rely on Vercel's server-provided `VERCEL_ENV=preview`; never `development` for an internet-accessible preview. | No |
| Local/developer `APP_ENV` | Missing classification now prevents startup/admin access. | Exact value `development` in local server environment. | Example and CI updated; each developer machine not verified |
| `ADMIN_EMAILS` by environment | This is the current server-side source of general admin authority. | Nonempty comma-separated list of named, current administrators; every entry is a complete email; no empty segments, shared accounts, wildcards, or test accounts in production. | No |
| `FLOOR_PLAN_REVIEWER_EMAILS` and `FLOOR_PLAN_PUBLISHER_EMAILS` | Approve/publish operations have narrower separation-of-duty policy. | Nonempty named lists in environments where these operations are used; every entry is a complete email with no empty segments; people and role separation match the approved operations model. | No |
| Google OAuth redirect URIs and application access | A valid session is the first admin prerequisite. | Only approved HTTPS origins/callbacks; local callback only for local OAuth client; test clients excluded from production. | No |
| Remote authorization-test sessions | HTTPS release testing must exercise real server sessions without writing through an unverified remote database connection. | Provision four distinct short-lived admin, ordinary, paid-Pro, and expired Auth.js test sessions in the dedicated non-production release database; supply their cookie headers only through the four `PLAYWRIGHT_*_SESSION_COOKIE` variables; the spec disables traces and validates the three negative identities through `/api/me`; revoke/delete every session immediately after the run. | No |
| Vercel deployment protection for previews | Preview URLs can contain admin surfaces and non-production data. | Approved access protection for staging/preview plus dedicated non-production database/secrets. | No |
| Vercel project/team roles and tokens | Release scripts use Vercel CLI authority, not application admin authorization. | Least-privilege named maintainers; protected production promotion; short-lived/scoped CI token; no token in repository. | No |
| GitHub required check | Repository CI contains the authorization matrix, but branch settings decide whether it blocks merging. | `Stable checks` and `Merge gate` required for protected branches; unauthorized workflow changes require review/CODEOWNERS as applicable. | Workflow inspected; branch settings not verified |
| GitHub environment protection for any future deploy job | The current workflow has no deploy job, but future deployment must not inherit ordinary CI authority. | Protected GitHub Environment with named approvers and environment-scoped credentials before adding deployment. | Not applicable today; setting not verified |
| Worker/maintenance runtime targets | Background imports, retention cleanup, deletion, integrity audit, and direct model utilities use shell plus database/filesystem/object-store authority rather than Auth.js. | Each scheduler/runbook supplies the intended exact `APP_ENV`, least-privilege environment-specific `DATABASE_URL`, and dedicated private-storage credentials; production destructive commands require named approval and a target check. Never give local/test fixture utilities production credentials. | Code now requires a recognized environment; concrete schedules, credentials, and targets not verified |
| Retention/deletion operating mode | Cleanup deletes private DB content and can drain permanent object deletions unless flags change its mode. | Scheduled cleanup uses a reviewed bounded limit; dry runs precede policy changes; ownership between cleanup and deletion worker is explicit; dead letters/lease loss are monitored; restore/retention policy is approved. | Implementation/docs inspected; scheduler and monitoring not verified |
| Database backup/restore custody and target | Shell scripts can export all records or apply arbitrary SQL; an environment label cannot itself prove a database URL is the intended target. | Named operator verifies project/host/database identity, uses least-privilege credentials and encrypted restricted backup storage, records approval, passes restore's exact environment confirmation, and verifies rollback/recovery. | Repository now requires explicit environment and restore confirmation; concrete target, custody, and approval not verified |
| Production/preview environment-variable edit audit | A configuration edit can intentionally remove all admin access or change named authority. | Platform audit logging retained and reviewed; alerts/change approval for `APP_ENV`, auth secrets, and admin/reviewer/publisher lists. | No |

Do not copy secret values into release evidence. Record only project/environment identifiers, the setting name, whether its value matches the secure state, the verifier, and timestamp.
