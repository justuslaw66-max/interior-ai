# Design document persistence contract

## Ownership and boundary

The persisted design document is owned by:

- `lib/design-document-contract.ts` for version constants, units, coordinate
  conventions, limits, tolerances, and runtime validation;
- `lib/design-document-migrations.ts` for ordered forward migrations;
- `lib/room-persistence.ts` for conversion between the domain snapshot and the
  transport/storage document;
- `lib/design-item-product-snapshot.ts` for immutable placed-product visuals;
- `lib/design-page-local-backup-recovery.ts` for local durability and recovery.

`DesignSnapshot` is the in-memory domain model. `StoredDesign` is the persisted
document. API payloads and database columns are transport details; they do not
define the document contract. A stored document may contain additive unknown
fields. Conversion and migration must retain those fields so a reader does not
silently erase data written by another compatible producer.

The database design ID is transport identity and remains outside document
content. A browser backup may carry `designId` as envelope metadata so it can
attempt a cloud refresh; that field is not a scene-object identity and is not
regenerated by document migration.

## Current version

The current document is major `version: 3`, `schemaRevision: 1`.

- A major version represents a structural compatibility boundary.
- A schema revision represents an additive or deterministic forward migration
  within the major version.
- Every new write includes `version`, `schemaRevision`, `units`, and
  `coordinateSystem`.
- Readers accept v1, v2, and v3 revision 0 through explicit migrations.
- A revision newer than this reader supports is rejected. It is never silently
  downgraded.
- No downgrade path is assumed or implemented.

Migrations are pure, deterministic, ordered, and idempotent. A migration clones
its input and returns either a validated current document or diagnostics that
identify the source version and failing paths. A failed migration never writes
over the source document.

## Identity and references

- `rooms[].id` is a stable room identity and must be unique.
- `activeRoomId` must reference an existing room.
- `rooms[].items[].instanceId` is a stable placed-object identity and must be
  unique across the document.
- `productId` and `variantId` identify the originating catalog selection.
- Cabinet and other domain-specific object IDs remain part of their owning
  item payload and are not regenerated during serialization or migration.

Runtime validation rejects missing, blank, duplicate, non-finite, or dangling
required identities. Errors expose codes, document paths, and actionable
messages without including private document contents.

## Coordinates, rotation, units, and tolerances

The scene is right-handed. Its origin is the center of the active room at the
finished-floor plane:

- +X points right;
- +Y points up;
- +Z points forward.

Canonical persisted units are:

| Field family | Unit |
| --- | --- |
| room geometry and wall/slab values | metres (`m`) |
| item positions and transform positions | metres (`m`) |
| product and cabinet dimensions | millimetres (`mm`) |
| `rotationY` and transform rotations | radians (`rad`) |
| finish texture rotations | degrees where the field name ends in `Deg` |

Display-unit conversion belongs at UI and export boundaries. Display choices
such as millimetres, centimetres, metres, feet, or inches are never written back
as if they were canonical geometry.

Central comparison tolerances are `0.000001 m` for position,
`0.000001 rad` for rotation, and `0.1 mm` for dimensions. Callers should use
these values instead of inventing persistence-specific rounding thresholds.

## Placed-product visual snapshots

Each persisted catalog item can carry `productSnapshot.schemaVersion: 1` with:

- product and variant IDs;
- saved product name and category;
- resolved dimensions in millimetres;
- saved variant label and finish identity;
- model, thumbnail, asset, and material-preset references.

This snapshot is the immutable visual fallback for the placed object. Existing
snapshots are not refreshed merely because the live catalog changed. If the
product or variant is removed or its geometry/assets change, the editor,
read-only viewer, plan, and exports can still preserve the saved visual meaning,
transform, and stable item identity.

Commerce is deliberately excluded from the snapshot. Price, stock,
availability, delivery, description, retailer links, and purchase URLs always
come from the current catalog. If no live catalog entry exists, the saved visual
is shown with a clear “purchase details unavailable / needs commerce” state; it
is never presented as currently purchasable from stale data.

## Runtime validation and size limits

Documents are validated at local read, local write, migration, and API ingress.
Validation checks the contract metadata, room/item structure, stable IDs,
references, finite transforms, positive geometry and dimensions, collection
limits, and product snapshots. Unknown additive fields are allowed and retained.

The maximum serialized document size is 4 MiB, with at most 100 rooms and 2,000
items per room. A size or validation failure is reported as a failed save; it is
not reported as success.

## Local durability and recovery

The active browser backup uses `interior-ai:v1:livingroom-design`. Two separate
namespaces provide recovery:

- `:last-known-valid` retains the most recent fully validated serialized copy;
- `:quarantine:<timestamp>` retains an unreadable source independently.

For a valid local write, the last-known-valid key is written before the active
key. Browser storage cannot provide a multi-key transaction, so this ordering
ensures a complete valid copy survives if the active-key write fails.

On an invalid mount-time backup:

1. validation and supported forward migration are attempted;
2. the raw source remains untouched and is copied to quarantine when storage
   permits;
3. hydration and all autosave paths remain blocked;
4. the user sees safe diagnostics and can download the raw backup, retry,
   explicitly open the last valid copy, or explicitly start a clean copy.

Starting clean removes only the active source. It does not delete quarantine or
last-known-valid data. There is no automatic cleanup of recovery data.

## Cloud saves and concurrency

Cloud autosave is debounced by 900 ms and writes are serialized through the
client write queue. Each loaded or created design records its database
`updatedAt` revision. Updates send that value as `expectedUpdatedAt`; the server
performs a conditional update inside the same transaction as floor-plan
reference synchronization. A stale revision returns HTTP 409 and the existing
save-status surface reports the conflict. The server never silently accepts a
stale overwrite.

The client document epoch prevents queued responses for a detached design from
being applied to a new draft. Cloud database writes are transactional. Local
backups remain available offline; cloud changes remain visibly pending or
failed until connectivity returns. Multi-tab automatic merging is not
implemented: conflicts require an explicit reload/reconciliation decision.

## Compatibility test fixtures

Historical v1 and v2 files live in `tests/fixtures/design-documents`. The
`verify:design-persistence` command covers migration, idempotence, unknown-field
retention, future-version rejection, product visual fallback, commerce
separation, local last-valid/quarantine behavior, API payload validation, local
backup normalization, and visible save-status behavior.
